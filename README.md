# 阿浪 · B 站游戏区冲浪 agent

我给一个 LLM 装上手脚和一份记忆，让它每天自己出门刷 B 站游戏区。

它不是我写死的推荐流——**代码不替它选题**。每整点它自己出门一趟，自己决定搜什么词、刷哪个
分区、精读哪条视频；读完自己写一段日记，再自己改口味画像。我给的只有六个工具（搜索 / 刷分区 /
精读 / 回忆 / 改口味 / 随手记）和一份记忆，判断权全交出去。

我做这个不是想造推荐系统，而是想看一件事：**一个 agent 的口味，能不能在没有任何标注数据的情况下，
靠阅读和自己的判断长出来。** 所以「用户画像」在这里不是一个功能模块，是主线——它每天读什么、
腻了什么、下一轮想钻哪条线，都是从画像里长出来的（实现见文末）。

`Python 3.10+` · 两个文件（`backend.py` + `crawler.py`）· 无外部数据库服务 · 单机单用户 demo

## 主要实现方式

```
                ┌───────────────────────────────────────────────────┐
   每整点 ─────▶│ 调度器（backend.py）                               │
   /api/surf    │  ├ 组上下文：兴趣画像 ＋ 用户反馈 ＋ 近几轮日记 ＋ 镜子 │
   反馈后触发    │  └ 工具循环（一轮内最多 26 次 LLM 往返）             │
                └──────────────────────┬────────────────────────────┘
                                       │ 六个工具；代码不替它选题
                ┌──────────────────────▼────────────────────────────┐
                │ crawler.py —— 只读采集层                           │
                │ WBI 签名 / cookie 预热 / 限速退避 / 错误分类        │
                └──────────────────────┬────────────────────────────┘
                                       ▼
        SQLite surf.db：videos / chunks（带向量）/ interest / diary / feedback / chat / usage_log
```

四条我认为值得单独说的：

### 1. 绝不把「没抓到」读成「没有」

这是整个项目最硬的一条。**它写的日记下一轮会被读回来当上下文**——一次把限流读成「这类内容
没人看」，那条错误认知就会在第 2、3、4 轮里越长越结实。所以空结果和失败在这套代码里从头到尾
是分岔的：

| 真实情况 | 怎么表示 | 喂给模型的话 |
|---|---|---|
| 搜索被软限流挡下 | 抛 `BiliThrottled`，动作记 `n=-1`（与真搜到 0 条的 `n=0` 分开） | 「这次被挡了，不代表这个词没内容，别写进日记」 |
| 评论接口在限流 | 单独留 `comments_error` 字段，不吞成空列表 | 「评论这次没抓到，不代表这视频没人评论」 |
| 接口不接受这个 rid | 前置拦下，不让下游抛异常再分辨 | 「是接口不认这个 rid，不是该分区没有新投稿」 |
| 分区名查不到 | 渲染成 `未知分区(tid=N)`，绝不留空串 | 空串会被读成「分区就是空的」；猜错的名字更糟，那是一条错误知识 |
| 刚发布的视频播放/评论真是 0 | 每条都带相对时间（「3 分钟前」） | 它才分得清「是刚发」还是「没抓到」 |

判据也统一成一条：**看键在不在，不看值真假**。真搜到 0 条时 `numResults` 的值是 0（假），
限流时这个键整个不见了——用取值判断会把两者正好判反。

### 2. 上下文是预算，不是垃圾桶

精读一条视频能抓回几千字，而工具循环每一轮都要把历史重发一遍，全塞进去代价是平方级的。

所以正文全部落 `chunks` 表（带向量），**只把摘要和最热几条评论还给模型**，要细节它自己调
`recall_memory` 做语义检索。评论按 10 条一组分块存——一个向量表示不了几十个话题，整坨塞进去
只会把相似度摊薄，捞出来又长又不对题。

量级没到之前，向量库是纯负债：检索就是几千条以内的暴力余弦，`numpy` 一次矩阵乘。

### 3. 它会照镜子

同一个词连搜七遍、一直在同一个分区打转，是这类 agent 最典型的自锁。两处对症：

- **换 `order`。** 同一个关键词，`pubdate` 序和默认相关度序几乎是两批人（实测只重叠 1/20）。
  工具描述里就写明：「一个词搜过一遍后，与其原样再搜，不如换 order 或换词」——换 order 只换人、
  不换话题，两者是两件事。
- **把计数摆给它看。** 出门前附一段「你最近几次动作」的计数：搜索了几次、同一个关键词占了几路、
  已读视频的类型分布。**只陈述计数，不评价、不指路**——判断留给它自己下。

### 4. 口口声声说反馈有用，那就得能验

`POST /api/ablation` 会把 `feedback` 表整个屏蔽，在同样的状态下再出门一趟，把两轮的工具调用
并排摆出来；差出来的那些动作，就是反馈真正改变的部分。它走的是同一套代码路径，只跳过写库那
一步（`dry_run=True`）——不是另写一份模拟，是真跑了一次，只是没留痕。

### 文件

| 文件 | 职责 |
|---|---|
| `crawler.py` | B 站只读采集层：WBI 签名、cookie 预热、限速退避、错误分类。不碰数据库、不碰 LLM |
| `backend.py` | FastAPI + SQLite + LLM 工具循环 |
| `envfile.py` | 手写 `.env` 解析（backend 与采集层自检共用） |
| `index.html` | 前端：日记、聊天、口味画像、已读视频 |
| `surf.db` | 运行时数据库（`-wal` / `-shm` 是伴生文件，一并忽略） |

**单文件不超过 800 行**是硬约束——加东西前先 `wc -l` 算预算。到天花板时正确的反应是压写法、
合并函数，不是拆文件。

### 边界与已知限制

- **评论翻页没打通。** 第二页改用 `pagination_str` 传 cursor 后，接口 `code=0` 不报错，却每次
  把第一页原样再发一遍，去重后一条新的都没有（紧凑 JSON 也试过，不是空格编码问题）。翻页逻辑
  在 `comments()` 里留着但默认关着——**别把 `limit` 调大，那只是每条视频白打 1~2 个请求**。
- **采集层只读。** 只调公开接口，不登录不发帖，请求间隔 ≥1 秒带抖动，失败指数退避，单次运行
  在百次以内。
- 单进程、单用户，没有并发优化。

## 快速开始

需要 Python 3.10+（开发环境 3.11.6）。

```bash
pip install -r requirements.txt
```

> `sentence-transformers` 会顺带装进 `torch` 和 `transformers`（本机实测 `torch==2.13.0` /
> `transformers==5.15.0`），体积不小。这两个故意没写死在 `requirements.txt` 里——它们版本敏感，
> 交给 pip 去解析；真跑不起来时再照上面两个版本回钉。
>
> `requirements.txt` **必须保持纯 ASCII**：pip 按系统区域编码读它，在 GBK 的 Windows 上，一个
> 中文注释就会让 `pip install -r` 直接抛 `UnicodeDecodeError`。

在项目根目录建 `.env`（**已被 `.gitignore` 排除，别提交**）：

```ini
DEEPSEEK_API_KEY=sk-...              # 必填，没有它启动会直接退出
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash

BILI_SESSDATA=...                    # 可选，见下
BILI_COOKIE=...                      # 可选，从 devtools 整行复制的 cookie

SURF_INTERVAL_SECONDS=3600           # 多久自己出门一趟
SURF_READ_PER_ROUND=12               # 每轮精读上限
DAILY_TOKEN_BUDGET=600000            # 每日 token 上限，超了就停
```

```bash
python backend.py
```

浏览器开 <http://127.0.0.1:8000>。

> 改完代码必须**重启进程**才生效：`init_db()` 和调度线程都在 `if __name__ == "__main__"` 里，
> 没有 `--reload` 这条路可走。

### 为什么建议填 SESSDATA

未登录也能刷榜（96 条）、能搜（20 条）、能拿弹幕（几百条），**唯一被卡死的是评论**：服务端只给
3 条预览，`ps` 给多大都没用——那是授权门槛，不是限流。而评论是这里唯一有实际内容的长文本，
没它 RAG 的语料薄得像纸。填 SESSDATA 是性价比最高的一步。

### 采集层自检

```bash
python crawler.py
```

不碰数据库，只读地打一遍 B 站接口，打印：登录态、排行榜条数、搜索、精读（含分区名），以及
「最新投稿和热度榜是不是两批池子」。**B 站接口一有变化，先跑它。**

## 用户画像是怎么实现的

前面那个 46 行的口味表不是截图，是它现在真实的记忆。这一节说它怎么长出来的。

### 画像不是标签表，是一组「分数 + 理由」

```sql
interest(topic TEXT PRIMARY KEY, score REAL, reason TEXT, updated_at REAL)
```

`score` 收在 0~2。冷启动给 7 条种子（「游戏」1.0，六个子分区各 0.6）——不给起点，它第一轮
无事可刷。之后每一条的分数和理由都由它自己维护。

### 两条更新通路

**它自己改**（`update_interest` 工具）：读完一批视频，模型自己决定给哪个主题加分减分，并写下
理由。上面那张表里「两轮追『谱面质量量化』都撞空……胃口被磨掉一半」就是它自己写的一句。
每次调用都记进当轮日记的 `actions`，事后翻得到。

**用户改**（`POST /api/feedback`）：你在前端给一条视频 👍 / 👎 之后，先过一次低温 LLM
（`derive_topic`）把「这一条」归纳成一个**可复用的主题词**，再落成分数变化：

```
delta = 0.18 × 0.7 × ±1        # 0.7 是用户权重——你说的话比它自己刷出来的观感更重
```

归纳失败就退回该视频的第一个标签，并写明「（归纳失败，退回首个标签）」——**不编一个主题出来**。

### 画像怎么被用回去

- 每轮出发前，`_interest_snapshot()` 把 top 8 摆进系统提示；
- 你说话时，同一份快照进对话的 system prompt；
- 被差评过的方向（`_negative_topics()`）会在搜索和精读命中时，在工具返回值里多出一行
  ⚠️「用户明确表示过不喜欢 X」——**让它自己决定要不要绕开，而不是硬拦**。

### 为什么是「分数 + 主题词」，不是向量

我要求画像满足三条，向量画像一条都不满足：

| 要求 | 分数 + 主题词怎么满足 |
|---|---|
| **可解释** | 每条带 `reason`，翻得到它当时在想什么 |
| **可审计** | `interest` 是一张普通表，每次改动都留在当轮日记的 `actions` 里 |
| **可反驳** | 用户能直接改分数，改完还能用 `/api/ablation` 验出改动的份量 |

一串 768 维的数字，三条都给不了。分档展示也是同一个道理：46 个主题平铺成一条连续谱什么也
看不出来，收成三档之后，颜色的密度就是它口味的形状。
